# Архитектура и реализация

Документ описывает, как устроено расширение **Ozon Product Collector** версии 1.0.0:
из каких модулей оно состоит, как данные проходят путь от DOM страницы Ozon до CSV/JSON,
как устроено хранилище и какие решения были приняты осознанно.

Смежные документы:

- [README.md](../README.md) — установка и использование;
- [CSV_JSON.md](CSV_JSON.md) — формат выгрузок;
- [SELECTORS.md](SELECTORS.md) — обновление селекторов;
- [ACCURACY.md](ACCURACY.md) — точность на контрольной выборке;
- [TESTING.md](TESTING.md) — тесты, нагрузка, браузерная проверка.

## 1. Назначение и границы

Расширение собирает карточки товаров только со **страниц выдачи Ozon** (поиск, каталог,
бренд, коллекция, продавец и т. п.), складывает их в локальное хранилище браузера и
экспортирует в CSV/JSON.

Что расширение **не** делает:

- не открывает карточки товаров, не переходит по ссылкам и не нажимает кнопки на Ozon;
- не покупает, не авторизуется и не обходит ограничения/капчу Ozon;
- не изменяет DOM страницы (только читает его);
- не отправляет данные на серверы, не содержит телеметрии и удалённого кода;
- не работает на главной ленте, страницах товара, в корзине и личном кабинете.

Ограничение по страницам задано в `isListingPage()` (`src/parser/url.ts`): URL должен быть
на хосте `ozon.ru`, путь не должен начинаться с `/product/`, `/cart`, `/order`, `/checkout`,
`/login`, `/my`, `/help`, `/reviews`, `/compare`, а также должен содержать `?text=` либо
начинаться с одного из префиксов выдачи (`/search`, `/category`, `/catalog`, `/highlight`,
`/brand`, `/collection`, `/seller`, `/productList`).

Один кодобаз — Chrome и Firefox. Различия сводятся к манифесту и способу запуска фонового
скрипта; прикладной код общий.

## 2. Технологии и сборка

| Слой | Решение |
| --- | --- |
| Язык | TypeScript, строгий режим |
| Сборка | esbuild, три entry point: `content`, `background`, `popup` |
| Формат бандла | IIFE, `platform: browser`, без sourcemap и минификации |
| Манифест | Manifest V3 |
| Хранилище | `browser.storage.local` / `chrome.storage.local` |
| Тесты | `node:test` + `jsdom`, Node 24 (нативное выполнение TypeScript) |
| Иконки | генерация PNG в `scripts/make-icons.mjs` |
| Упаковка | `zip` в `scripts/build.mjs` |

`npm run build` создаёт:

```
dist/chrome/    + dist/ozon-collector-chrome.zip
dist/firefox/   + dist/ozon-collector-firefox.zip
```

Сборка не использует `eval`, `new Function`, внешние CDN, WASM и динамические импорты.
Все зависимости попадают в бандл на этапе сборки.

### Отличия манифестов

| Поле | Chrome | Firefox |
| --- | --- | --- |
| `background` | `service_worker: background.js` | `scripts: [background.js]` |
| Минимальная версия | `minimum_chrome_version: 111` | `strict_min_version: 142.0` |
| Специфичные настройки | — | `browser_specific_settings.gecko` |
| Идентификатор | — | `ozon-product-collector@local.extension` |
| Заявление о данных | — | `data_collection_permissions.required: ["none"]` |

Firefox 142+ требуется из-за обязательного `data_collection_permissions`; сами
используемые WebExtensions API существуют давно. Chrome 111 выбран как минимальная
удобная версия с MV3.

### Права доступа

```json
"permissions": ["storage", "unlimitedStorage"],
"host_permissions": ["https://*.ozon.ru/*", "https://ozon.ru/*"]
```

`tabs` не запрашивается: popup получает активную вкладку через `tabs.query`, что доступно
без разрешения `tabs` (URL приходит только для хостов, на которые есть host permissions).
`downloads` не нужен — файл сохраняется через `Blob` + `<a download>` внутри popup.

## 4. Общая схема потока данных

```
страница Ozon (listing)
  DOM
   → MutationObserver
   → debounce 500 мс
   → requestIdleCallback
   → findCardRoot(link) → extractCard(root)
   → CardExtraction (поля + field_states)
   → signature (защита от повторной отправки)
   → pending[] (2.5 с или 25 карточек)
   → runtime.sendMessage
        ↓
background (единственный писатель, serial())
   → ingestBatch(sessionId, cards, sourceUrl)
   → нормализация → quality guard → дедупликация
   → storage.local: products, observations, session, meta, state
   → badge + ответ со счётчиками
        ↓
popup (storage.onChanged + polling 1.5 с)
   → runtime.sendMessage(data:export)
   → CSV/JSON → Blob → download
```

Сеть не используется ни на одном шаге.

## 5. Content script

### 5.1. Инициализация

`src/content/index.ts` при загрузке:

1. Проверяет, что `location.hostname` принадлежит `ozon.ru`; иначе выходит.
2. Ждёт `document.body`.
3. Читает `state` из `storage.local` и создаёт/останавливает сканер.
4. Подписывается на `storage.onChanged` (смена состояния из popup/background).
5. Подписывается на сообщения background: `collector:flush`, `collector:changed`,
   `collector:cleared`.
6. Ставит `popstate`, `hashchange`, Navigation API (`navigation.navigate`), если доступен,
   и резервный `setInterval` раз в 2 секунды для SPA-переходов.
7. На `beforeunload` делает финальный `flush()`.

Сбор активен только если одновременно:

```ts
alive && state.enabled && state.active_session_id && isListingPage(location.href)
```

То есть открытая вкладка товара или корзины не приводит к сбору, даже если сессия включена.

### 5.2. Сканер и MutationObserver

`CardScanner` (`src/content/scanner.ts`) не сканирует DOM на каждую мутацию. Колбэк
`MutationObserver` только вызывает `kick(500)`, который сбрасывает и заново ставит таймер.
Это защищает от штормов мутаций при бесконечной прокрутке и виртуализированных списках.

После debounce работа выполняется в `requestIdleCallback` (timeout 1200 мс) или, если API
недоступен, через `setTimeout(0)`. За один проход обрабатывается не более 12 карточек или
~12 мс; остаток очереди переносится на следующий idle-слот. Дополнительные «пинки» —
через 800 и 2500 мс после старта: Ozon часто дорисовывает карточки после первого кадра.

Для каждого `a[href*="/product/"]` вызывается `findCardRoot()`:

1. Сначала `link.closest()` по списку `CARD_ROOT_SELECTORS` (от специфичных
   `[data-widget="searchResultsV2"] .tile-root` к общим `.tile-root`, `[class*="tile"]`).
   Кандидат принимается, если внутри 1–8 товарных ссылок, а текста меньше 6000 символов.
2. Если ничего не найдено, подъём по родителям до 12 уровней ищет ближайший
   `div/article/li/section` с 1–4 ссылками, деньгами или изображением.

Такой fallback нужен, потому что Ozon меняет классы и оборачивает плитку в дополнительные
контейнеры. Он также не даёт принять за карточку всю страницу.

### 5.3. Учёт обработанных карточек

Для каждого корня в `WeakMap<Element, ProcessedState>` хранится:

```ts
{
  status,          // success | partial | failed
  attempts,        // сколько раз пытались извлечь
  lastAttemptAt,
  signature,       // отпечаток последнего успешного/неуспешного результата
  retryScheduled,
  quick            // дешёвый отпечаток DOM
}
```

`quick` — это конкатенация `href` всех товарных ссылок и первых 120 символов текста.
Если виртуализированный список переиспользовал тот же DOM-узел под другой товар,
`quick` изменится, состояние сбросится и карточка будет извлечена заново.

`signature` включает URL, название, цену, зачёркнутую цену, рейтинг, отзывы, продавца,
наличие и статус извлечения. Множество `emitted` не даёт повторно отправлять тот же
результат, если React перерисовал плитку с теми же данными.

При смене сессии, URL или после очистки вызывается `resetPage()`: очищаются `processed`,
`emitted`, очередь, кеш JSON-LD и `currentUrl`.

### 5.4. Повторы извлечения

Если карточка получилась `partial` или `failed`, она ставится в `retryQueue` и повторяется
через 1.5 с и 4 с — максимум два повтора (три попытки всего). Повтор помечается
`is_update = true`, чтобы background:

- обновил наблюдение и поля товара;
- **не** увеличивал `cards_discovered` (это не новое обнаружение);
- не создавал ложный рост счётчиков.

Если узел отключён от документа (`!root.isConnected`), повтор пропускается.

### 5.5. Батчинг и доставка в background

Content script не пишет в хранилище напрямую. Найденные карточки складываются в `pending`:

- обычная задержка — 2500 мс;
- при накоплении 25 карточек — 100 мс;
- одновременно выполняется только один `flush()` (`inFlight`);
- в одном сообщении уходит не больше 25 карточек (лимит `ingestBatchSize`);
- сообщение содержит `sessionId`, `sourceUrl`, `searchQuery` и массив `cards`.

Обработка ответа:

| Ответ | Действие |
| --- | --- |
| `ok: true` | пакет принят |
| `session_not_found` | состояние перечитывается, пакет не повторяется |
| `quality_rejected` | пакет отклонён background, повтор не нужен |
| `storage_error` / сеть / исключение | пакет возвращается в начало очереди, до 3 повторов |
| `invalid_payload` | пакет отбрасывается |
| «extension context invalidated» | сканер останавливается, очередь очищается |

При ошибке записи background выставляет warning в `state`; content повторяет отправку,
поэтому временный сбой `storage.local` не теряет данные, пока вкладка жива.

## 6. Извлечение карточки

`extractCard(root, context)` (`src/content/card-extractor.ts`) — единственное место, где
DOM превращается в доменную запись.

### 6.1. Выбор ссылки

Среди всех `a[href*="/product/"]` внутри карточки выбирается ссылка с самым длинным
текстом (плюс бонус за `aria-label`). Кнопки «Купить», «В корзину» штрафуются. Ссылка
нормализуется:

- отбрасываются query/hash и подстраницы (`/reviews`, `/questions`, `/similar` и т. п.);
- `product_id` извлекается из числового хвоста слага (5+ цифр);
- канонический URL: `https://<host>/product/<slug>/`;
- `normalized_url` — тот же URL без завершающего `/`, используется для дедупликации.

### 6.2. Название

Кандидаты собираются из `TITLE_SELECTORS`, выбранной ссылки и всех товарных ссылок.
Каждый текст оценивается:

- длина (до 300);
- бонус за `<a>`, за принадлежность выбранной ссылке, за классы `tsBody500Medium`,
  `tsBodyControl500Medium`, `title`;
- бонус за листовой узел;
- штраф за контейнер-ссылку с вложенными элементами (чтобы бейджи «Хит», «−35%» не
  приклеивались к названию);
- штраф за `<img>`, слова «отзыв», «продавец», длину > 500.

Отбрасываются generic-тексты: «Купить», «В корзину», цена, число, «Ozon», «Продавец»,
«N отзывов». Если ничего не найдено, последний резерв — `alt` изображения внутри ссылки;
такой текст всё равно берётся из карточки.

### 6.3. Цены

Цены — самая сложная часть, потому что на карточке одновременно могут быть:

- обычная цена;
- зачёркнутая (старая) цена;
- цена с Ozon Картой;
- цена по подписке;
- цена за единицу/месяц;
- стоимость доставки;
- несколько вариантов в одном контейнере.

Алгоритм:

1. Собираются элементы, текст которых содержит ровно одно денежное совпадение и не длиннее
   90 символов. `script/style/noscript/template/svg` игнорируются.
2. Каждый кандидат получает score: размер шрифта × 10 + длина текста + бонус за классы
   `price`/`headline`/`tsheadline` + бонус за листовой узел.
3. Зачёркнутость определяется по `<s>/<del>/<strike>`, inline `line-through`, классам
   `line-through`/`strikethrough`/`old-price`/`price-old` и `getComputedStyle`.
4. Условия («с Ozon Картой», «по подписке», «за 1 шт.», «в месяц») ищутся сначала в самом
   элементе, затем в ближайших родителях. Если рядом несколько цен, условия не наследуются,
   чтобы не приписать «по подписке» обычной цене.
5. Основная цена — лучший не зачёркнутый кандидат, не являющийся месячным, за единицу или
   по подписке. Если таких нет, допускается подписочная.
6. Старая цена — максимальная зачёркнутая. Если она меньше основной, она отбрасывается и
   добавляется ошибка `original_price:lower_than_current`.
7. Отдельно выбираются `ozon_card` и `subscription`; все остальные осмысленные цены
   попадают в `prices.other` (с дедупликацией).
8. Текст доставки исключается.
9. `price_type` выводится из условий основной цены: `regular`, `ozon_card`, `subscription`
   или `unknown`.

Если в карточке есть символ валюты, но основная цена не распознана, ставится
`field_states.price = "failed"`, а не «нет цены». Это важно для контроля качества: «поле
отсутствует» и «поле есть, но не разобрано» — разные состояния.

### 6.4. Остальные поля

| Поле | Источник |
| --- | --- |
| `currency` | знак/код валюты из цены |
| `original_price` | зачёркнутая цена |
| `discount`, `discount_text` | только явные метки скидки (`−35%`, «Скидка 35%») |
| `volume`, `volume_unit` | разбор названия: `75 мл`, `2 × 75 мл`, `1 л`, `200 г` |
| `quantity` | множитель из названия (`2 × 75 мл` → 2) |
| `seller` | блок продавца; generic-значения вроде «Ozon» отбрасываются |
| `rating` | текст рейтинга рядом с отзывами |
| `review_count` | «123 отзыва», «1,2 тыс. отзывов» |
| `availability` | «В наличии» / «Нет в наличии» |
| `price_conditions` | человекочитаемое условие основной цены |

Объём и количество извлекаются **только из названия** и только при однозначном совпадении.
Если в названии несколько объёмов или единиц, значение не выдумывается: поле остаётся
`null`, а в `extraction.errors` появляется пометка.

### 6.5. JSON-LD как резерв

`readJsonLd()` один раз на URL читает все `script[type="application/ld+json"]` (не более
500 товаров, глубина до 8, размер скрипта до 2 МБ). Поддерживаются `Product`, `sku`,
`productID`, `offers.price/lowPrice/priceCurrency`, `aggregateRating`.

JSON-LD используется **только для полей, которые не удалось получить из видимой карточки**:
название, `product_id`, цена, валюта, рейтинг, число отзывов. Каждое такое поле попадает
в `extraction.fallback_fields`, чтобы это было видно в выгрузке. JSON-LD никогда не
перезаписывает корректно извлечённое видимое значение.

### 6.6. Состояния полей и статус

Для каждого из 13 полей (`FIELD_NAMES`) хранится одно из:

- `extracted` — значение найдено и разобрано;
- `absent` — в карточке нет признаков поля;
- `failed` — признаки есть, но парсер не справился.

Инвариант: поле не может быть `extracted`, если значение `null`. Это проверяется и в
экстракторе, и в репозитории.

Итоговый статус:

| Условие | Статус |
| --- | --- |
| есть URL + название + цена | `success` |
| есть URL и хотя бы название или цена | `partial` |
| иначе | `failed` |

`extraction.errors` содержит машиночитаемые пометки (`price:present_but_not_parsed`,
`title:present_but_not_parsed`, `original_price:lower_than_current` и т. п.).
`extraction.extraction_version` фиксирует версию DOM-парсера
(`1.0.0-dom.1`), чтобы по данным можно было понять, каким кодом они собраны.

## 7. Background script

`src/background/index.ts` — единственный компонент, который пишет в `storage.local`.
Это устраняет гонки между вкладками: даже если открыто десять вкладок Ozon, все записи
проходят через один экземпляр background.

### 7.1. Сериализация операций

```ts
let serialChain = Promise.resolve();
function serial<T>(task: () => Promise<T>): Promise<T> {
  const run = serialChain.then(task, task);
  serialChain = run.then(() => undefined, () => undefined);
  return run;
}
```

Через `serial()` проходят:

- `collector:start`;
- `collector:stop`;
- `cards:ingest`;
- `data:clear`;
- `data:export`;
- обработчики `onInstalled` / `onStartup`.

Даже если предыдущая операция упала, следующая всё равно выполнится.

### 7.2. Валидация сообщений

Для `cards:ingest` проверяется:

- отправитель — это же расширение (`sender.id === runtime.id`);
- payload содержит строковый `sessionId` и массив `cards`;
- `sourceUrl` берётся из `sender.url`, если это Ozon, иначе из payload; если валидного
  Ozon-URL нет — сообщение отклоняется.

Это защищает от записи данных со сторонних страниц и от случайных сообщений.

### 7.3. Запись и повторы

`ingestCards()` вызывает `repository.ingestBatch()` через `retry(..., 3, 250)`:
до трёх попыток с задержками 250 и 500 мс. После успеха обновляется badge.

Если запись всё равно не удалась:

- в `state.warning` записывается понятное сообщение;
- content script получает `storage_error` и возвращает пакет в очередь;
- данные не считаются принятыми, счётчики не растут.

Badge показывает число уникальных товаров активной сессии (`999+` при переполнении) и
очищается, когда сбор выключен.

### 7.4. Жизненный цикл

- `runtime.onInstalled` — инициализация и обновление badge.
- `runtime.onStartup` — если сессия была активна, она переводится в `interrupted`
  с предупреждением. Сбор **никогда не возобновляется молча** после перезапуска браузера.
- `startCollection()` — если осталась незавершённая сессия, она закрывается как
  `interrupted`, затем создаётся новая.
- `stopCollection()` — просит все вкладки сделать `flush()`, затем закрывает сессию,
  обнуляет `active_session_id`, обновляет badge.
- `clearData()` — останавливает активную сессию, вызывает `repository.clearAll()`,
  восстанавливает дефолтные `state/meta/session_index` и рассылает вкладкам
  `collector:cleared`.

### 7.5. Экспорт

Экспорт формируется в background, а не в popup:

1. popup отправляет `data:export` с `scope` (`all` или `session`), `session_id`, `format`;
2. background собирает `ExportBundle` из хранилища;
3. `buildExport()` формирует строку CSV/JSON, имя файла и MIME;
4. popup создаёт `Blob` и инициирует скачивание.

Так popup не дублирует логику выборок и не держит тяжёлые данные в памяти дольше нужного.
Имя файла содержит дату и область: `ozon-products-YYYY-MM-DD.csv`,
`ozon-observations-YYYY-MM-DD.csv`, `ozon-data-YYYY-MM-DD.json`; для экспорта одной
сессии префикс меняется на `ozon-session-`.

## 8. Хранилище

### 8.1. Схема ключей

| Ключ | Значение |
| --- | --- |
| `p:<16 hex>` | `ProductRecord` — актуальное состояние товара |
| `pidx:<n>` | массив ключей `p:` (чанк индекса, до 100) |
| `session:<id>` | `SessionRecord` — полная сессия |
| `obs:<session>:<n>` | массив `ObservationRecord` (чанк, до 100) |
| `session_index` | массив `SessionSummary` для быстрого списка |
| `state` | `CollectorState` — включён/выключен, активная сессия, warning |
| `meta` | `DbMeta` — число товаров и чанков индекса |

Почему так:

- `storage.local` перезаписывает значение ключа целиком. Если хранить все товары одним
  массивом, каждая вставка переписывала бы всю базу. Отдельный ключ на товар даёт запись
  размером с один товар.
- Индекс и наблюдения разбиты на чанки по 100, чтобы не росла стоимость одной записи.
- `session_index` отделён от `SessionRecord`: popup нужен только список, а полный список
  ключей товаров и счётчик чанков наблюдений — только при экспорте.
- `unlimitedStorage` снимает квоту `storage.local`, которая иначе быстро исчерпывается
  историей наблюдений.

IndexedDB не используется: нужен простой, предсказуемый API, который одинаково работает
в Chrome и Firefox, легко тестируется через `KeyValueStore` и не требует транзакционной
модели. Плата — отсутствие атомарности между ключами (см. раздел 12).

### 8.2. Дедупликация

Ключ дедупликации:

```
id:<product_id>          если product_id найден
url:<normalized_url>     иначе
```

`product_id` берётся из URL карточки, а если его нет — из JSON-LD. Для хранения
используется `p:<fnv1a64(dedupe_key)>`. Это стабильный 64-битный хеш, одинаковый в
Chrome и Firefox (BigInt, без зависимости от платформы).

Коллизия обрабатывается честно: если по ключу уже лежит запись с другим `dedupe_key`,
добавляется суффикс `~1`, `~2`, … и ключ перечитывается. Внутри одного пакета
повторяющиеся карточки сначала схлопываются в `Map<dedupe_key, card>` — на один товар
приходится одно наблюдение за пакет.

Сессия хранит `product_keys`, поэтому экспорт по сессии не сканирует всю базу.

### 8.3. Слияние товара

`ProductRecord` — это **последнее известное состояние**, а не последний снимок. Правило:

```ts
title: card.title ?? existing.title
price: card.price ?? existing.price
```

То есть новое непустое значение обновляет поле, а `null` **никогда не стирает** уже
известное. Это осознанное решение: если Ozon не отрисовал продавца в виртуализированной
плитке, это не означает, что продавец исчез.

Исключения:

- `price_type` и `price_conditions` обновляются только вместе с новой ценой;
- `prices` заменяется, если в карточке есть хотя бы одна цена, иначе остаётся прежний набор;
- `first_seen_at` не меняется;
- `last_seen_at` — время последней записи background;
- `collected_at` — время последнего обнаружения, давшего это состояние;
- `observation_count` увеличивается на 1 на каждое уникальное обнаружение;
- `session_ids` и `source_urls` пополняются с ограничением 20 и 10 элементов.

Наблюдение (`ObservationRecord`), наоборот, хранит **снимок на момент обнаружения**,
включая `null`. Поэтому история позволяет видеть, как менялись цены и какие поля
пропадали. CSV товаров — это текущее состояние, CSV наблюдений — история.

### 8.4. Сессии

`SessionRecord` содержит:

- `session_id` (`sess-<uuid>`), `started_at`, `finished_at`;
- `initial_url`, `search_query`;
- `status`: `active` | `stopped` | `interrupted`;
- `cards_discovered`, `unique_products`, `errors`, `partial`, `success`;
- `observation_count`, `observation_chunks`;
- `product_keys` — ключи товаров, встреченных в сессии;
- `extraction_versions`, `note`.

Правила счётчиков:

- `cards_discovered` растёт на число **новых обнаружений** (`is_update !== true`);
- повторы извлечения не увеличивают этот счётчик;
- `unique_products` = размер `product_keys`;
- `errors` — число `failed`-обнаружений;
- `partial` и `success` — соответствующие статусы;
- `observation_count` — число записанных наблюдений.

Сессия переживает перезагрузку вкладки: `active_session_id` хранится в `state`, поэтому
после reload content script продолжает ту же сессию. После перезапуска браузера
`onStartup` переводит её в `interrupted` — это защита от «фонового» сбора без ведома
пользователя.

## 9. Quality guard

Массовое изменение разметки Ozon не должно тихо записывать мусор. После нормализации
пакета `analyzeBatch()` считает:

- `total` — сколько карточек пришло;
- `validIdentity` — у скольких есть `product_id` или URL;
- `title` — у скольких есть название;
- `price` — у скольких есть цена;
- `success/partial/failed`.

Правила для пакетов от 5 карточек:

| Условие | Реакция |
| --- | --- |
| identity < 80% **или** title < 60% | пакет **отклоняется** (`quality_rejected`), в `state.warning` пишется объяснение |
| price < 50% **или** success < 50% | пакет сохраняется, но выставляется предупреждение |
| иначе | пакет сохраняется без предупреждения |

При отклонении:

- товары и наблюдения не пишутся;
- `cards_discovered` и `errors` сессии всё равно растут на число обнаружений;
- возвращается `ok: false`, `code: "quality_rejected"`;
- content не повторяет пакет;
- пользователь видит предупреждение в popup.

Порог в 5 карточек выбран, чтобы одиночная нестандартная карточка не блокировала сбор.
Проверка «identity» спасает от ситуации, когда селекторы корня ещё работают, а ссылки
уже нет; проверка «title» — от ситуации, когда вместо названия извлекается бейдж.

## 10. Экспорт

`ExportBundle` собирается репозиторием:

- `scope: "all"` — все товары, все сессии, все наблюдения;
- `scope: "session"` — только `product_keys` выбранной сессии и её наблюдения.

Сортировка:

- товары — по `first_seen_at`;
- наблюдения — по `collected_at`;
- сессии в `session_index` — по `started_at` (новые первыми).

CSV:

- UTF-8 BOM, чтобы Excel корректно открывал кириллицу;
- CRLF;
- экранирование кавычек, запятых и переводов строк;
- массивы (`session_ids`, `source_urls`, поля извлечения) — через `;`;
- `other_prices` — компактный JSON;
- пустые значения — пустая строка, а не `null`/`undefined`.

JSON содержит `schema_version`, `exported_at`, `scope`, `session`, `sessions`, `products`,
`observations`, `stats`. Подробный контракт — в [CSV_JSON.md](CSV_JSON.md).

При экспорте всех товаров используется чанковый индекс `pidx:*`. Если индекс повреждён
или запись была прервана, срабатывает self-healing: при `keys.length < meta.product_count`
репозиторий читает все ключи и добирает `p:*`. Это медленнее, но не теряет данные.

## 11. Popup

Popup — только UI и транспорт сообщений. Он не читает и не пишет доменные ключи напрямую.

Что показывает:

- статус «Сбор включён/выключен»;
- карточки, уникальные товары, ошибки — по активной/последней сессии;
- всего товаров в хранилище;
- текущий/последний URL, время старта и последнего извлечения;
- предупреждение quality guard;
- версию расширения, браузер и версию парсера.

Как обновляется:

- `runtime.sendMessage({ type: "state:get" })` при открытии;
- `storage.onChanged` с задержкой 250 мс;
- резервный polling раз в 1.5 с.

Действия:

- «Начать сбор» — передаёт URL активной вкладки, если это страница выдачи Ozon;
- «Остановить» — останавливает сессию и просит вкладки сбросить очередь;
- выбор области экспорта: все данные, текущая сессия или конкретная сессия;
- три кнопки экспорта: товары CSV, наблюдения CSV, JSON;
- «Очистить данные» — с подтверждением, необратимо.

Кнопки блокируются во время операции (`busy`), чтобы не отправить две команды подряд.
Список сессий перестраивается только при изменении «отпечатка» (активная сессия + список
id), чтобы не сбрасывать выбор пользователя на каждом обновлении.

## 12. Надёжность и крайние случаи

| Ситуация | Поведение |
| --- | --- |
| Вкладка перезагружена | сессия та же, сканер стартует заново, дубликаты отсекаются дедупликацией |
| Браузер перезапущен | сессия `interrupted`, сбор не возобновляется |
| SPA-переход | `popstate`/`hashchange`/Navigation API + резервный интервал 2 с; `resetPage()` |
| Виртуализированный список | `quick`-отпечаток замечает подмену DOM-узла |
| Повторная отрисовка той же карточки | `signature` в `emitted` не даёт повторной отправки |
| Ozon изменил разметку | quality guard отклоняет/предупреждает, счётчики ошибок растут |
| `storage.local` временно недоступен | background retry ×3, content requeue ×3, warning в state |
| Очистка во время сбора | сессия останавливается, вкладки получают `collector:cleared` |
| Открыто несколько вкладок | все пишут через один background, операции сериализованы |
| Сессия удалена/не найдена | `session_not_found`, content перечитывает состояние |
| Контекст расширения инвалидирован | сканер останавливается, очередь очищается |

Ограничение: `storage.local` не даёт транзакции на несколько ключей. Запись товара,
наблюдения, сессии и индекса выполняется одним `set()`, но браузер не гарантирует
атомарность на уровне «всё или ничего» при сбое питания. Сериализация и self-healing
индекса снижают риск, но не устраняют его полностью. Для текущего объёма данных этого
достаточно; при переходе на десятки тысяч товаров стоит рассмотреть IndexedDB.

## 13. Производительность

Мероприятия, заложенные в архитектуру:

- `MutationObserver` не выполняет тяжёлую работу, только debounce;
- извлечение идёт в idle-слотах по 12 карточек;
- повторные карточки не извлекаются повторно;
- запись — пакетами, а не по одной карточке;
- индекс и наблюдения — чанками;
- экспорт читает ключи чанками по 100;
- JSON-LD парсится один раз на URL, а не на карточку.

По нагрузочному тесту (`docs/TESTING.md`) 1000 товаров импортируются за ~39 мс и
экспортируются за ~43 мс в `MemoryStore`; 5000 — за ~187/194 мс. Это не скорость
`storage.local`, а проверка отсутствия квадратичной деградации. Реальная запись в браузере
медленнее из-за сериализации и квот.

## 15. Точки расширения

Чтобы добавить новое поле:

1. добавить имя в `FIELD_NAMES` и тип в `src/shared/types.ts`;
2. извлечь значение в `card-extractor.ts` и выставить `FieldState`;
3. провести поле через `normalizeCard()` и `ProductRecord` в `repository.ts`;
4. добавить колонку в `PRODUCT_HEADERS`/`OBSERVATION_HEADERS` и строки CSV;
5. обновить `docs/CSV_JSON.md`, README и тесты.

Чтобы обновить селекторы:

1. править только `src/content/selectors.ts`;
2. поднять `EXTRACTION_VERSION`;
3. прогнать тесты и `npm run accuracy`;
4. проверить на живом Ozon по чек-листу из `docs/SELECTORS.md`.

Чтобы добавить браузер/формат:

- браузер — новый манифест в `scripts/build.mjs` и, при необходимости, ветка в
  `src/adapters/browser.ts`;
- формат — новый `ExportFormat`, ветка в `buildExport()` и кнопка в popup.

## 16. Ключевые решения (кратко)

1. **Один background-писатель.** Убирает гонки между вкладками и упрощает счётчики.
2. **Отдельный ключ на товар + чанковые индексы.** Запись не переписывает всю базу.
3. **Дедупликация по `product_id`, затем по нормализованному URL.** Ozon не всегда даёт
   числовой id, но URL достаточно стабилен.
4. **`null` не стирает известные значения.** Виртуализация DOM не должна обеднять данные.
5. **Наблюдения — снимки, товар — merged-состояние.** Позволяет и анализировать историю,
   и быстро выгружать актуальное.
6. **`field_states` вместо «пустых строк».** Отличает отсутствие поля от ошибки парсера.
7. **Quality guard.** Массовая поломка разметки не должна тихо портить базу.
8. **JSON-LD только как fallback.** Видимая карточка — приоритетный источник.
9. **Явный старт/стоп и `interrupted` после перезапуска.** Сбор всегда требует согласия.
10. **Минимум разрешений и полный офлайн.** Нет сети, телеметрии и удалённого кода.

## 17. Известные ограничения

- Реальные селекторы Ozon не проверены на живом сайте из-за HTTP 403 в среде разработки;
  они покрыты синтетическими карточками и требуют ручной сверки.
- Эвристики названия, продавца и цены могут ошибаться на нестандартных карточках
  (например, наборы, товары с несколькими вариантами, рекламные блоки).
- JSON-LD может быть устаревшим или неполным; он используется только как fallback.
- `storage.local` не транзакционен; при аварийном завершении возможна частичная запись.
- Нет фонового сбора: работает только открытая вкладка выдачи.
- Нет синхронизации между устройствами и профилями браузера.
- Chrome-поведение MV3 service worker при длительном простое не проверялось браузерным E2E.
- Очень большие базы (десятки тысяч товаров) лучше выгружать по сессиям; JSON на 5000
  товаров занимает ~14 MiB.
